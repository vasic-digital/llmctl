## Memory policy (OD-14, FR-083)

No artificial ceiling below the machine: `MemoryHigh = MemoryMax = probed total RAM` for every unit including the gateway. Measured peak of the decision gateway process (`VmHWM`, idle after start-up, TLS key/CA generated): **16376 kB** in the live systemd run, 19-20 MB in the test run. Measured peaks of the engines depend on the model and are recorded by the GPU/CPU QA sets, not by the harmless stand-in engine used here.

## macOS honesty statement

No Mac is available to this suite. `launchctl` is never executed. The gateway and encoder-runtime LaunchAgents are generated by the real backend code and validated as files (python `plistlib` structure, mode 0600, `ProgramArguments` array, `KeepAlive`, `ThrottleInterval`, no key material) plus the dry-run `launchctl` command lines. Whether launchd accepts and runs them is **not proven**. Registry liveness on macOS uses `ps -o args=` (gap G-009) and is fixture-tested only. A launchd `KeepAlive` respawn does not rotate the engine key (no `ExecStartPre` equivalent); rotation happens on every `llmctl start`.

## Findings made while building this

* The installed operator unit `~/.config/systemd/user/llmctl-llama@.service` (generated by the previous `llmctl install`) has `StartLimitIntervalSec` in `[Service]`; `systemd-analyze --user verify` reports `Unknown key ... ignoring`. The restart interval was silently the default. The new templates put both settings in `[Unit]`; re-run `llmctl install` to refresh an existing installation.
* `registry reconcile` health-checks https rows against the CA given by `LLMCTL_CACERT` (default `$HOME/llmctl/cert/ca/ca.crt`); a caller whose gateway uses another `LLMCTL_HOME` must pass the matching `LLMCTL_CACERT`, otherwise the gateway row is removed as "unverifiable" (seen in the live transcript).
