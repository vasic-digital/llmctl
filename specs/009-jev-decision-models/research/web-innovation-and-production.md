## 2. Detail by area

### 2.1 Observability

**Metrics (items 2, 3).** Prometheus text exposition (`Content-Type: text/plain; version=0.0.4`) is a plain line format that can be written without a client library [P2 *(snippet)*]. Follow the naming page: application prefix, base units (`_seconds`, `_bytes`), `_total` for counters, `_ratio` for 0–1 values, and never put unbounded values in labels [P1]. Suggested set (all names INFERRED design, not from any source):

- `llmctl_decide_requests_total{type,status}` — `type ∈ {yesno,choice,scale}`, `status ∈ {ok,client_error,model_error,timeout,rejected}`.
- `llmctl_decide_duration_seconds{type}` histogram. Bucket advice: exponential, 5–10 buckets, top bucket above expected p99 [P0 *(snippet)*]. For a one-pass 0.8B–4B model start around 0.01…10 s; for the DeBERTa encoder with one pass per option, extend to 30 s (encoder cost grows with option count — D-10).
- `llmctl_decide_options` histogram (option count), `llmctl_decide_confidence_ratio` histogram (buckets every 0.1 — this is the raw material for live ECE comparison).
- `llmctl_decide_state_truncated_total` (FR-012), `llmctl_decide_auth_failures_total` (never labelled by presented key), `llmctl_decide_abstained_total`.
- `llmctl_decide_queue_depth` gauge, `llmctl_decide_inflight` gauge, `llmctl_decide_rejected_total{reason}` (queue_full, draining, too_large).
- `llmctl_instance_up{profile,instance}` gauge, `llmctl_model_info{profile,sha256_prefix,revision} 1`.
- **Trap:** do not label with question name, profile-specific free text, client key name unless the key set is small and operator-defined, or request ID. Cardinality is the failure mode the naming page warns about [P1].
- The engine behind generative profiles can expose its own metrics only if started with `--metrics` [L1]. Per FR-073 the engine port is loopback-only, so the gateway scrapes it internally and re-exports a curated subset; do **not** expose it to the network.
- The `/metrics` endpoint must follow FR-019 (key required) or be on a separate operator-only listener; making it unauthenticated leaks traffic shape (INFERRED).

**Health vs readiness (item 3).** Kubernetes defines liveness (restart if wedged, should not check external dependencies), readiness (can it take traffic now) and startup (slow init) [K1]. Map: `/healthz` = process alive, no model detail (satisfies FR-021); `/readyz` = model loaded and a canary one-token call succeeded within N s, returns 503 while loading (the engine already does this for `/health` [L1]), and returns 503 first during drain. Keep both minimal and unauthenticated per FR-021 or put `/readyz` behind the key — decide in planning; unauthenticated readiness lets a LAN scanner learn "model loaded" (INFERRED, low impact).

**Logs and audit (item 4).** One JSON object per line to stderr/journald: `ts, level, request_id, route, status, profile, instance, type, n_options, latency_ms, truncated, abstained, key_name (not value), state_sha256`. Request ID: accept a client `X-Request-Id` only if it matches a strict regex (length, charset), otherwise generate; echo it in the response header. The state hash lets an operator prove "this call was this input" without storing text — but a low-entropy state (e.g. "yes") is trivially reversible by dictionary; use `HMAC-SHA256(per-install-secret, state)` rather than a bare hash (INFERRED). Rotate with `logrotate`/journald, not custom code.

**Tracing (item 35).** OTLP/HTTP supports a JSON encoding that is marked Stable for traces, metrics and logs, endpoints `/v1/traces` etc. [OT1]. A search for a released Python-only JSON exporter found only a *planned* `opentelemetry-exporter-otlp-json-http` and protobuf exporters [OT2 *(snippet)*]. So a hand-rolled `urllib` POST of a few spans is technically feasible (INFERRED) but adds a maintenance burden for little gain at single-host scale. ADOPT-LATER, off by default. GenAI semantic conventions exist but the page moved to a separate repo; I could not read attribute stability [OT3] — do not adopt names until read.

**SLOs (item 2/3).** Suggested starting SLIs (INFERRED design): availability = non-5xx non-429-by-us / valid requests; latency = share of valid requests under a per-profile threshold measured *on this host class*; correctness is **not** an online SLI — it comes from the golden set (#13). Alerting pattern from Google's workbook: page at burn 14.4× (1 h long / 5 min short window) and 6× (6 h / 30 min); ticket at 1× (3 d / 6 h); short window = 1/12 of long [SRE1]. These numbers assume a 99.9% SLO and are "reasonable starting numbers" per the source; for a single-host local service that is too strict — pick 99% and say so. A shipped `docs/runbooks/` page with these queries is more valuable than an alert manager integration.

### 2.2 Calibration and quality

**Metrics (item 5).** ECE = bin-weighted |accuracy − confidence|; MCE = max over bins; Brier = mean squared error of the probability vector [C1]. Guo-style temperature scaling fits one scalar on a held-out set and does not change argmax, hence accuracy [C1]. For llmctl, apply T to the option **letter log-probabilities** then renormalise; fit T by minimising NLL on a labelled CSV (golden-section search is stdlib-only, INFERRED). Honest caveats to print every time: n, number of non-empty bins, bootstrap CI for ECE; refuse to fit below a minimum n (suggest 200, INFERRED, not sourced). `Jev.md`'s "ECE > 0.15 do not use in production" and "< 0.05 good" thresholds are un-sourced guidance from the conversation (l.1802–1806) — label them so.

**Which confidence?** Spec FR-015 already says confidence is a shaping convention. A 2025–26 line of work compares token log-prob confidence with verbalized confidence for judge-style tasks and reports mixed results depending on model generation [C2 *(snippet)*]; the one-token letter read-out is the former. Do not claim calibration without the profile file.

**Calibration profile file (item 5).** `~/.llmctl/calibration/<profile>.json` with: `temperature`, `fit_dataset_sha256`, `n`, `ece_before/after`, `brier_before/after`, `model_sha256` (so it auto-invalidates when the model changes), `llmctl_version`, `created`. Server applies it only when the model sha matches; otherwise ignores it and says so in `/readyz` detail (authenticated). This is the "provenance" the spec's FR-052 wants.

**Order-bias probe (item 6).** Selection bias in multiple-choice LLM answers is largely a *token bias toward option IDs* (A/B/C…), reported as accuracy swings from ~13% to ~75% across 20 models/3 benchmarks when options are reordered [B1]. Probe: for each golden question, run all cyclic rotations (N passes), report (a) **flip rate** = fraction of questions whose chosen option *content* changes across rotations, (b) per-letter prior (how often each letter wins), (c) accuracy by position. Report cost clearly (N× passes). PriDe-style debiasing estimates the letter prior from a small permuted sample and subtracts it at inference [B1]; that is a clean ADOPT-LATER because it needs a stored prior per model — which fits the calibration profile. The `Jev.md` figures 30.3% vs 1.8% flip rate are un-verified conversation claims (source-findings §E); cite only measured results.

**Voting across instances (not in backlog as NOW).** Self-consistency (Wang et al.) votes over *sampled reasoning paths*; its gains (e.g. GSM8K +17.9%) come from sampling diversity [SC1 *(snippet)*]. A temperature-0 one-token decider run twice on the same model returns the same answer, so "vote across instances of one model" adds nothing (INFERRED) — the `Jev.md` suggestion of a "different warmup seed" (l.2066) has no mechanism behind it. Voting only helps across **different models**, and then only if their errors are decorrelated (unmeasured). Ship a measurement tool (`decide compare --models a,b,c` on the golden set, reporting agreement and majority accuracy) before any gateway voting feature. Variance reporting = disagreement fraction, not a standard deviation.

**Abstention (item 7).** Selective classification: predict only when confidence ≥ θ, trading coverage for lower risk; the risk–coverage curve summarises it [A1 *(snippet)*]. Add optional `min_confidence` (request-level) returning the normal probabilities plus `"abstain": true` and no `choice`; ship `llmctl decide risk-coverage labelled.csv` to pick θ. Keep the field additive so hosted-compatible clients are not broken (verify against the hosted shape, which is vendor-documented — source-findings §E).

**Deterministic regression suite (item 1, 13).** Facts to design around:
- llama.cpp warns logits are not bit-identical across batch sizes when prompt caching is on [L1]. Thinking Machines measured that load-dependent batch size is the main cause of temp-0 variation, and that batch-size-1 execution would be deterministic; making kernels batch-invariant cost ~2× at first, ~1.6× with better attention [T1]. vLLM added a batch-invariant flag and SGLang a deterministic mode with ~34% average throughput loss *(snippets)* [T2].
- Therefore: golden/regression runs use the engine with one slot, prompt cache off, fixed seed (greedy readout has no sampler seed to matter, INFERRED), and compare **structurally**: exact equality of `choice`/`abstain`, probabilities within an absolute tolerance (suggest 1e-3 for GGUF, tighter for ONNX; INFERRED, calibrate by repeating runs), and hash-pin the *rounded* output (e.g. 6 decimals) plus the model sha, template version and engine build. A pinned hash then detects model/template/engine drift, while the tolerance band avoids false failures from kernel noise. SC-001's "byte-identical" must be scoped to this deterministic mode and the CLI evidence rounding must be specified, or SC-001 will be flaky on a loaded host.
- Frozen benchmark: JSONL of ≥30 questions (SC-003) with expected answers, a SHA-256 manifest, a baseline (always-first, majority) computed by the same tool, provenance label per number (FR-052). Report accuracy with a Wilson/bootstrap interval — with n=30 the interval is wide; saying "exceeds baseline" needs that interval honestly shown (INFERRED statistics, not sourced).

### 2.3 Production serving

- **Backpressure (14).** Cap in-flight and queued requests per instance; reject with `429` + `Retry-After` (RFC 6585 status, header defined in RFC 9110 for 429/503, value = seconds or HTTP-date) [R1]. Use `503` + `Retry-After` while draining. Add a per-request cost cap before queueing (FR-016: encoder = one pass per option).
- **Graceful drain (15).** SIGTERM → mark not-ready → stop accepting → finish in-flight up to a deadline → exit; set `TimeoutStopSec` above the deadline. systemd documents SIGTERM then SIGKILL after `TimeoutStopSec` and `Type=notify` with `READY=1`/`STOPPING=1`/`WATCHDOG=1` over `NOTIFY_SOCKET` [D1 *(snippet)*]. The protocol is a datagram to a unix socket, so Python stdlib `socket` suffices (INFERRED); not needed for 3.1.0 — `Type=simple` + a correct SIGTERM handler is enough. launchd has no equivalent; document macOS as best-effort.
- **Warm-up (readiness).** First request after load is slow (graph build, page-in). `/readyz` should run a canary decision before reporting ready; log the warm-up latency (INFERRED).
- **Zero-downtime model switch.** Only possible when two instances fit the memory budget at once (FR-027/029). Honest statement: with the §12.6 60% RAM ceiling a swap of a ~2.7 GB or ~9.5 GB model usually needs headroom for both for a short time; when admission control refuses, the documented behaviour is "stop old, start new, brief outage". Implement as `llmctl decide rollout <profile>` = start new instance on a spare port → wait `/readyz` → flip gateway upstream → drain old (INFERRED design). ADOPT-LATER (L2 of FR-029 first).
- **Config reload.** SIGHUP re-reads limits, quotas and calibration profile only; never the key or certificate path without a restart (so FR-058 "never regenerated silently" remains simple). ADOPT-LATER, S.
- **Cache (20).** Key = SHA-256 over canonical JSON of `{model_sha256, template_version, calibration_profile_sha, question, state, params}`; TTL + LRU in an `OrderedDict`; revision change changes the key so no explicit invalidation is needed (INFERRED). Partition by tenant key name: shared prefix/result caches can leak information through timing — a 2026 paper title on "prefix caching side channels in shared LLM systems" exists [X1 *(snippet)*]; I did not read it, so treat the exact attack as unverified and just partition. Report hit ratio in `/metrics`. Never cache `error` results.
- **Engine-side prefix reuse.** llama.cpp can reuse KV state for a shared prompt prefix per slot (`cache_prompt`), with prefix-affinity slot choice *(snippet)* [L2]. If the prompt template puts the *state* first and the *question/options* last, several questions about the same state share a long prefix (INFERRED). That is a measurable speed-up for multi-question requests — but it is exactly the setting that costs bit-exactness [L1]. Offer it as a throughput mode with the determinism trade-off stated; default off.
- **Resource guards.** Keep admission control as the single authority (FR-027). Add a startup self-check that prints the 60% ceiling arithmetic; reject `--parallel` values that would exceed it. `--parallel N` multiplies context by N in llama.cpp *(snippet)* [L3], so slot count directly drives memory — expose it as an admission input, not a free knob.
- **Idempotency (32).** Decisions are read-only pure functions of (model, input); retries are inherently safe (INFERRED). The IETF `Idempotency-Key` header is still an Internet-Draft (draft-07, Oct 2025) *(snippet)* [ID1]. Accept and echo it in logs for correlation; no store.
- **Multi-tenant keys (21, 22).** The product value is real (separate keys per agent, revocation, per-client quotas). **But FR-057 says exactly one credential variable and bans the candidate's second variable.** Resolve in planning: keep `LLMCTL_API_KEY` as the primary key and add an *optional* file `~/.llmctl/keys.json` (mode 0600; entries `{name, sha256(key), scopes, not_before, not_after, rate}`) — no new env var, no change to FR-058 precedence. Rotation overlap = two entries valid simultaneously, old one with `not_after`. Store only digests; compare with `hmac.compare_digest` (D-23). Scopes: `decide`, `metrics`, `admin`. Flag as spec amendment.
- **mTLS (23).** Python `ssl`: server context `CERT_REQUIRED` + `load_verify_locations(client_ca)` [SS1 *(snippet)*]. Value is service-to-service where a bearer key is undesirable. Complexity is distributing client certs; `llmctld` already issues mTLS material for its nodes (INFERRED from `internal/mtls`), so a future unification is plausible but unproven. Keep optional and off by default.
- **OpenAI-compat without chat (9, 33).** `/v1/models` is already planned (toolkit discovery). For agents that "only speak chat/tool calling": generate a function/tool definition per question type from the single schema. OpenAI strict mode requires `additionalProperties:false` and all fields required *(snippet)* [O1]. The agent's host executes the tool by calling llmctl; the decision model never sees a chat message. Do **not** add `/v1/chat/completions` to decision endpoints (backlog 33).

### 2.4 Developer and agent integration

- **MCP server (10).** MCP tools are model-controlled with a human-in-the-loop SHOULD; servers MUST validate inputs, rate-limit and sanitise outputs; clients SHOULD log tool usage [M1]. Tool results may carry `structuredContent` (JSON) plus a text copy for compatibility, and tools may declare `outputSchema` that the server MUST satisfy [M1]. Proposed tools: `decide_yes_no`, `decide_choose`, `decide_score`, plus `check` as a thin yes/no alias (names obey the spec's allowed characters [M1]). Implement as a small stdlib stdio JSON-RPC loop that calls the HTTPS endpoint with the FR-058 key resolution and the FR-068 trusted certificate — the key must be read from env/`.env`, **never** written into an MCP client config file (agents commit those). I did not fetch the stdio framing and `initialize` handshake pages, so "feasible with stdlib only" is INFERRED; verify the handshake in the spec before estimating. Confused-deputy risk: any prompt-injected agent can ask the tool about arbitrary state; the tool is read-only but its answers may gate actions — document.
- **Claude Code hook template (11).** Hooks can be shell commands, HTTP POSTs, MCP tool calls, prompt or agent hooks; `PreToolUse` can block; exit code 2 is the only code that blocks by itself, exit 1 is non-blocking; decisions are returned as `permissionDecision: allow|deny|ask|defer` [H1]. HTTP hooks treat non-2xx as non-blocking [H1], i.e. **fail open**. Consequences (INFERRED): (a) ship a *command* hook (`llmctl decide hook claude-code`) that maps probabilities to `permissionDecision` and chooses explicitly: shadow (always allow, log), enforce-fail-open, or enforce-fail-closed (exit 2 on endpoint error); default shadow, matching the `Jev.md` rollout; (b) an HTTP hook would need the self-signed cert trusted by Claude Code's HTTP client — unknown, so not recommended; (c) do not teach the gateway Claude's hook JSON (couples the decision API to one agent).
- **opencode (11).** Plugins can intercept `tool.execute.before` to alter args or block, and register custom tools via a `tool` helper [H2]; HTTP from plugins is possible through Bun/Node libs (not documented) [H2]. Template = a JS plugin shelling out to `llmctl decide` rather than re-implementing TLS trust.
- **Other agents (pi, crush, aider, continue, Cline).** I did not research their extension points; the spec's FR-035 needs per-agent tested instructions anyway. For agents without hooks, the integration is "agent runs `llmctl decide` as a shell tool / MCP tool" (INFERRED).
- **Slash commands / completions (8).** Ship `llmctl completion bash|zsh` generated from the one command table (no completion code exists in the repo today — grep found none). Slash commands are agent-specific; provide them only in the docs per agent.
- **CLI ergonomics (8).** `--stdin` (read state from stdin, avoids shell-history leakage and argv length), `--jsonl` batch (one request per line → one result per line, stable order, per-line errors), `--explain` (print the rendered prompt, tokenised option letters and the log-prob table; never prints the key), `--dry-run` (render only, no inference — also the cheapest test of FR-009 single-template). `--explain` doubles as the debugging tool for D-01 truncation.
- **OpenAPI 3.1 + conformance (12).** 3.1 is fully aligned with JSON Schema 2020-12 and supports bearer/apiKey/mutualTLS security schemes [S0]. Write `docs/openapi.yaml` by hand (small endpoint set), then a stdlib test that (1) walks the document's paths/methods and fails if any is missing from the FR-069 inventory, and (2) validates sample responses against the response schemas. `jsonschema` is importable on this host but is not stdlib — a user-facing test must not assume it; dev-time use is fine. Schemathesis generates property-based tests from an OpenAPI 3.1 schema, `st run`, with minimal `curl` reproducers [S1]; it is pip-installable but not installed here, and I could not confirm its dependency footprint or offline use [S1]. Recommendation: not a release gate (needs installs); document as an optional pre-release fuzz run, and give the gate a table-driven stdlib fuzz (oversize, wrong types, huge option counts, non-object body, truncated JSON) which maps directly to D-07/D-08/D-09.

### 2.5 Enterprise and operations

- **SBOM (17).** CycloneDX 1.6 supports a `machine-learning-model` component type with a model card *(snippet)* [SB1]; pip-audit can emit CycloneDX (and audits requirement files, `--require-hashes`) *(snippet)* [V1]. Plan: a hand-assembled CycloneDX JSON listing (a) pinned Python packages with hashes (FR-025), (b) each shipped model as an ML-model component with source repo, revision, size, sha256, licence (FR-002/003), (c) the vendored engines at their pinned tags. This also yields the NOTICE content. Tool-generated SBOMs (syft etc.) are not installed here; defer.
- **Licence audit / NOTICE.** Apache-2.0 §4 requires keeping attribution and carrying an upstream NOTICE when one exists; MIT requires keeping copyright and permission notices *(snippet)* [LI1]. A quantised GGUF is a derivative; the safe reading is that it carries the original licence plus the converter's attribution (INFERRED — the search found nothing specific). A model advertised Apache-2.0 but fine-tuned from a restrictively licensed base may not be redistributable *(snippet)* [LI1]: the admission gate (FR-007) must record the **base model** licence chain, not just the card's licence field. Ship `NOTICE` generated from the catalog.
- **Vulnerability scanning (V1).** pip-audit uses the Python Packaging Advisory Database via PyPI JSON and OSV, so it needs network at scan time *(snippet)* [V1]; run it as a maintainer pre-release check with the output stored as evidence, not as an installed dependency. The encoder runtime's pinned `onnxruntime`/`sentencepiece` set is the whole Python attack surface — keep it tiny and hash-pinned (D-16).
- **Signing and provenance (18, 19).** Practical for a solo maintainer: SHA-256 manifest + `gpg --detach-sign --armor` (gpg exists on this host); minisign is an Ed25519 tool with tiny keys and signatures but is not installed *(snippet)* [SG1]; cosign can sign blobs with a local key and `--tlog-upload=false`, verifying with `--insecure-ignore-tlog` *(snippet)* [SG2] — useful offline, but not installed here. SLSA: Build L1 = provenance exists (a laptop can reach it); L2 = hosted platform generates and signs the provenance — **not reachable from the maintainer's machine**; L3 needs a hardened platform [SL1]. So publish a `provenance.json` (builder, commit, inputs, commands, archive hashes) and label it **SLSA Build L1 equivalent, self-attested**. Claiming L2 would be a false claim and also contradicts the project's no-hosted-CI rule (FR-055).
- **Reproducible archives (16).** Recommended tar flags: `--sort=name --mtime=@$SOURCE_DATE_EPOCH --owner=0 --group=0 --numeric-owner --pax-option=exthdr.name=%d/PaxHeaders/%f,delete=atime,delete=ctime`; gzip with `-n`; zip with `--no-extra` [RB1]. The release script today omits all of these, and I found no `.env` exclusion (D-30). Add both, then a test that builds twice and compares hashes, and one that plants a `.env` and proves it is absent.
- **Data protection statement.** Facts the statement may truthfully include (all from the spec/design, none telemetry-related): inference is local; the only outbound traffic is model download from the pinned host; state is not written to logs (hash only); the key and certificate stay on disk with owner-only permissions. Add: the audit log's HMAC secret lives in the state dir. Do not claim "GDPR compliant" — not a property a tool can have (INFERRED).
- **Backup/restore and upgrade.** Back up exactly: `.env` (key), `llmctl/cert/*`, calibration profiles, `keys.json`, the catalog overlay, and unit files are regenerable. Provide `llmctl backup` (tar of those paths, mode 0600, refuses to write under the repo tree) and `llmctl restore --dry-run`. Upgrade = `git pull` + re-render units + migrate state-dir layout with a `state/VERSION` marker and a one-step rollback (keep the previous rendered units). The decision-state layout is new in 3.1.0, so there is no legacy decision state to migrate; existing chat installs are untouched (spec Clarification 2).
- **Runbooks to ship:** (1) 401s after upgrade/rotation, (2) certificate expired/name mismatch/clock skew, (3) instance not ready/stuck loading, (4) queue full/429 storm, (5) disk full during download (partial files must not look complete — spec edge case), (6) key lost, (7) model sha mismatch, (8) backend killed mid-request, (9) high ECE alert → disable abstain-reliant automation, (10) rollback.
- **Capacity planning guide.** Inputs from the existing planner: per-instance footprint (measured, FR-027), `--parallel` slot count, context per slot; outputs: instances × slots; plus a worked example for this host. Include measured p50/p95 per profile (llmctl-measured label) — from SC-003/010 runs, not vendor numbers.
- **Chaos/fault plan** (each is a test with captured evidence; maps to FR-038 stress/chaos and SC-006): kill the engine mid-request (expect typed 502, no hang, gateway recovers); SIGSTOP the engine (expect timeout, not thread exhaustion); fill the state directory/disk (expect refusal at start, no partial `.env`/cert); `chmod` cert unreadable; expired cert (use a back-dated test certificate, FR-070); clock skew via a test-only faketime wrapper in a namespace (never change the host clock — §12 host safety); stale pidfile pointing at an unrelated process (D-05); concurrent first start (one key); SIGTERM during load (drain); client slow-loris and oversize bodies (D-09). Remember Constitution host-safety: no suspend/reboot, respect memory ceiling.

### 2.6 Game changers — honest assessment

Maturity key: **proven** (widely used, I read a source), **plausible** (published results, not on this stack), **speculative**.

1. **Cascade (24) — plausible, high upside, needs #5.** The decider returns a confidence; route low-confidence items to a larger model. FrugalGPT reports matching GPT-4 with up to 98% cost reduction in its setting [F1]; RouteLLM reports >85% cost reduction on MT-Bench at 95% of GPT-4 quality, but only 45% on MMLU and 35% on GSM8K [F2] — the savings are task-dependent, which is the honest headline. For llmctl the measurable claim would be "% of decisions the local model resolves at ≥θ with accuracy ≥ target on *your* shadow data". That needs calibration, labelled data and a teacher — all of which are items 5/7/25 first. Do not market a savings number before measuring it; the `Jev.md` token-saving rules are un-sourced estimates.
2. **Distillation from shadow logs (27) — proven in general, out of scope here.** Teacher→BERT-scale student results (e.g. 130× faster/25× cheaper in one Amazon system, secondary source) [Q1 *(snippet)*]. For llmctl this means: the shadow-mode JSONL (#25) is the dataset; a training pipeline is a separate feature (spec Out of Scope). The cheap step now is making the log schema training-ready (state text opt-in with consent, label, teacher id) so the option is not foreclosed.
3. **Constrained decoding (28) — proven for chat models, orthogonal to decision profiles.** llama.cpp supports grammars and JSON-schema constraints [L1]; libraries report very low per-token masking cost *(snippet)* [CD1]. It is the right tool for "a small chat model must return valid JSON", but a decision profile does not generate JSON — it reads one token's log-probs. Adding it here would invite using chat models as deciders and blur FR-006. Keep as a separate, later "structured output" capability if ever wanted.
4. **Embedding + kNN / SetFit (29) — plausible, needs labelled data and training.** Competitive with ~8 examples/class on sentiment *(snippet)* [SF1]; latency would be tiny. But it is a different product (trained classifier per question set), not a Jev-like zero-shot decider. Reject for this feature.
5. **Apple silicon (30) — avoid.** MLX is reported faster than llama.cpp on many models on recent chips, and ~50% slower at 30K+ context in one community test *(snippets)* [ML1]. Decision prompts are short, so MLX might win — but adding an engine means new pins, new tests, new unit types, for an unverified gain. llama.cpp Metal already runs on macOS. Revisit only with a measured decision-latency gap on real hardware.
6. **WebGPU/WASM client (31) — avoid.** Transformers.js runs ONNX models via WASM/WebGPU, but WebGPU is "experimental… inconsistent support" *(snippet)* [W1]; the DeBERTa export here is 1.74 GB, hopeless for a browser. No user need in the spec.
7. **Federation via `llmctld` (26) — plausible, unknown.** The Go daemon has Raft, mTLS node routes and replication packages locally. I could not establish whether its scheduler understands the `decide` capability or per-instance slots; read `llmctld/internal/cluster` and `executor` before designing. A minimal, honest first step is *client-side* spreading across multiple gateway URLs (the spec's FR-029 already requires spreading) and documenting `llmctld` placement as a follow-up.
8. **GPU sharing with chat models — verified locally as a constraint, not a feature.** This host has ~4.8 GiB free GPU with a vision server running (spec Assumptions). The mitigation is already FR-027 (refuse with numbers); the product opportunity is a `plan` view showing "decide-tiny on CPU alongside chat on GPU" (INFERRED).
9. **Differentiators that are cheap and real:** (a) a *local, auditable* decision layer with calibration profile + order-bias report shipped in the box — the hosted service cannot offer reproducibility of the model; (b) deterministic mode with hash-pinned golden outputs (#1, #13); (c) "typed question → tool definition for any agent" (#9). None needs new research.

## 3. Do NOT do (over-engineering traps)

1. Do not add `/v1/chat/completions` (or any chat route) to decision endpoints, or pick a decision profile for chat — breaks FR-006 and US4-3.
2. Do not put the OpenTelemetry Python SDK, `prometheus_client`, `schemathesis`, `hypothesis` or `pip-audit` into the **runtime**; they are not installed on user hosts and widen the supply chain (FR-025). Dev/maintainer-time use only.
3. Do not claim SLSA L2/L3, "tamper-proof", or "GDPR compliant" for a laptop-built, self-signed release.
4. Do not vote across identical instances of one temperature-0 model; no mechanism produces a gain (INFERRED), and `Jev.md`'s +2–10% figures are unverified.
5. Do not default-enable request batching, `cache_prompt`, or a result cache before the golden regression suite exists and shows byte/tolerance stability; they weaken FR-010/SC-001 [L1][T1].
6. Do not label metrics with state, question names, request IDs or key values; do not expose `/metrics` or the engine `--metrics` port to the network unauthenticated.
7. Do not log a bare SHA-256 of low-entropy state as "privacy-safe"; use an HMAC.
8. Do not add a second credential environment variable for extra keys; use a 0600 keys file (FR-057).
9. Do not implement an Idempotency-Key store; decisions are pure and the header is still a draft.
10. Do not build distillation/training, an embedding-kNN decider, MLX, or a WebGPU client in 3.1.0.
11. Do not make the Claude Code integration an HTTP hook to the self-signed endpoint: non-2xx is non-blocking (fail-open) and TLS trust is unverified [H1].
12. Do not publish a "tokens saved" or "% cost saved" number without a measured shadow-data run labelled llmctl-measured.
13. Do not trust any hash, size, accuracy or repo name in `Jev.md` (source-findings §E); admission is by re-verification only.
14. Do not change the host clock, kill unrelated processes, or fill the real disk in chaos tests (Constitution §12).
